## Database Design

| Column Name    | Datatype    | Not Null | Primary Key |
|----------------|-------------|----------|-------------|
| created_at     | TIMESTAMPTZ | ✅       |             |
| updated_at     | TIMESTAMPTZ | ✅       |             |
| id             | UUID        | ✅       | ✅          |
| published_date | DATE        | ✅       |             |
| status         | SMALLINT    | ✅       |             |
| title          | TEXT        | ✅       |             |
| description    | TEXT        |          |             |
| image_url      | TEXT        |          |             |

> [!important]
> - For high-traffic systems with very large PostgreSQL tables that containing millions/billions of rows, arranging fixed-width columns by decreasing alignment requirements can reduce tuple alignment padding; potentially minimize row/ storage size. This technique is called "**Column Tetris**".
> - For this optimization, order fixed-width table columns by decreasing alignment requirements.
>   - 8-byte alignment types: `bigint`, `bigserial`, `double precision`/ `float8`, `timestamp`, `timestamptz`, `time`, `interval`
>   - 4-byte alignment types: `integer`, `serial`, `real`/ `float4`, `uuid`, `date`
>   - 2-byte alignment types: `smallint`, `smallserial`
>   - 1-byte alignment types: `boolean`
>   - Variable-width types (at last): `numeric`, `text`, `character varying`/ `varchar`, `bytea`
> - However, it's ok to follow a more readable column format, when your table schema changes frequently.

## Design Decisions

> [!tip]
> Modern languages like Rust provide ergonomic language features(Cargo, crates and workspaces) to manage complex projects with more optimized incremental and parallel compilation. Also, thin handlers can be written and attached directly to a struct containing dependencies (`AppState`) to enforce compile-time guarantees without relying on additional layers.
> 
> > [!important] 
> > Rust doesn't eliminate DDD, Clean Architecture, etc.; But it reduces the need to express architectural boundaries through technical layers because Rust language features themselves can provide those boundaries directly.

- This project has started as a Rust workspace to ensure future scalability.
- We choose [Hyper](https://github.com/hyperium/hyper), [Axum](https://github.com/tokio-rs/axum), [Tokio](https://tokio.rs) and [Tower ecosystem](https://github.com/tower-rs) as they are the most stable and prominent HTTP server ecosystem at the moment of writing.
- We choose [Toasty ORM](https://github.com/tokio-rs/toasty) as it is the most future-proofing object relational mapper at the moment of writing.
- We choose [Garde](https://github.com/jprochazk/garde) for input validation and [Utoipa](https://github.com/juhaku/utoipa) to generate the OpenAPI specification for our project.
- We choose [Docker](https://docs.docker.com/get-started/get-docker/) ([OrbStack for macOS users](https://orbstack.dev)), [Docker Compose](https://docs.docker.com/compose/) for development setup and [PostgreSQL](https://www.postgresql.org) for the database.
